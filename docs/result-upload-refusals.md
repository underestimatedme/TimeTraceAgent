# 结果上报被服务器反复拒收（HTTP 409）：停止自动重试，原始结果保留

适用：Runner 把一次执行的结果事件（`running`、`completed`、`failed`……）上传给 Valley，Valley 回复 HTTP 409。

## 行为

- Valley 现在的通用 409（错误码 40900）同时覆盖租约失效、该尝试已终结、序列缺口等情况，**一次 409 不能证明结果没有送达，也不能证明永远送不到**。
  所以第一次 409 之后仍按原来的节奏（60 秒）重试。
- 同一批（任务 / 尝试 / 租约代次）**连续 5 次**（`OUTBOX_REFUSED_PAUSE_AFTER`）被 409 拒收后，Runner **不再自动发送这一批**。
  这一状态写在本机 SQLite（表 `remote_outbox_hold`），重启 Runner、过一小时、过一个月都不会自己恢复发送。
- 停止的只是“自动发送”。事件内容、序列号、`observed_at` 发生时间、入队时间原样保留；**不会**标记为已送达（`sent_at` 仍为空），
  **不会**标记为用户手动废弃（`abandoned_at` 仍为空），也不会放开旧租约或重新执行任务。
- 这一批不影响别的执行、别的尝试、心跳、领取新任务和审批快速路径：停止后的批次连查询都不进入上传循环。

## 计数语义（两个数不要混）

| 字段 | 位置 | 含义 |
| --- | --- | --- |
| `failures` | `remote_outbox_retry` | 这一批所有类型的失败总数（409、5xx、超时……），只用于退避和诊断展示，**不用于判定停止**。 |
| `refused` | `remote_outbox_hold` | 这一批**连续**收到 HTTP 409 的次数。任何其它失败会把它归零；收到 ACK 时整行删除。 |

- 同一个等待窗口内到达的两个 409（普通上传和审批快速路径同时被拒）只算一次确认。
- 不算拒收、永远不会被停止：401（走原有授权恢复）、网络错误、超时、响应无法解析、5xx、429 限流、成功提交但回执丢失。
  这些按 5 秒起翻倍、上限 30 秒的退避无限期重试，只有收到服务器确认（ACK）才标记已送达。

## 旧版数据库

旧版 Runner 对 409 每 60 秒重发一次、从不停止（现场见过 13,181 与 1,373 次）。但它在 `remote_outbox_retry` 里只留下三样东西：
**最后一次**失败的状态、**所有类型**失败的累计次数、下次重试时间。这不能证明服务器一直在回复 409：4 次 500 加 1 次 409 是 5 次失败、最后一次 409，
13,181 次连续 409 也是“很多次失败、最后一次 409”。所以**升级本身不会停止任何批次**，也不会把“最后一次 409”说成“此前一直回复 409”。

升级后第一次打开数据库时，只对 `remote_outbox_retry` 中最后一次是 409、累计失败不少于 `OUTBOX_LEGACY_CHECK_AFTER`（60 次，
即旧版每分钟一次重试约一小时）、仍有未送达事件的批次写一条**待核对**记录（`remote_outbox_hold.basis = legacy_check`，`paused_at` 为空，
`legacy_failures` 记下旧的累计次数）。其余批次（包括 4 次 500 加 1 次 409 这类少量混合失败）不做任何标记，按新批次从 0 开始计连续拒收。

待核对批次的**下一次新请求**（普通上传或审批快速路径，先到先得，合计一次）决定它的去向：

| 服务器的答复 | 结果 |
| --- | --- |
| ACK | 原始事件原样标记已送达，记录清除；与新批次完全一样。 |
| 再次 HTTP 409 | 立即停止自动发送（`basis = legacy_refused`，`refused = 1`），这是升级后总共多发的**一份**请求。依据是两件事实：旧记录（累计 N 次失败、最后一次 409）加这次新的 409；doctor 与日志都分开写明。 |
| 网络错误、超时、无法解析、401、429、5xx | 不是拒收：不计入连续拒收，仍按原来的 5 秒起翻倍、上限 30 秒的退避重试，待核对标记保留，等到服务器真正答复（ACK 或 409）为止。 |

每个批次这一步只发生一次：已有记录的批次（新版计数过的、已核对过的、人工恢复过的）重开数据库不会被再次标记或停止。
停止后的事件、序列号、`observed_at`、入队时间、`sent_at` / `abandoned_at` 与旧版留下的完全一致。

## 诊断

- `timetrace agent doctor` 对已停止的批次显示：停止原因与时间、保留的条数与序列范围、最早入队时间、事件发生时间范围，
  并说明 409 的含义不确定，同时给出下面两条可执行命令。停止原因按来源分开写：连续 5 次 409（`confirmed`）；
  或“升级前旧版本累计失败 N 次、最后一次 409，升级后核对一次仍是 409”（`legacy_refused`）。
- 待核对的批次在 doctor 里显示为“结果上报待核对”，只陈述旧记录（累计次数、最后一次 409），并说明这不能证明服务器现在仍会拒收；
  核对请求遇到网络错误或 5xx 时，另加一行最近的答复和下次重试时间。它还在自动发送，所以不提供 `retry-results`。
- Runner 日志每个进程对每个已停止批次只写一行，对每个待核对批次也只写一行（说明将重新发送一次来核对）。
- 匿名结构：`Database.remote_outbox_health()`，只有计数、一个原因码（`http_409`）和 epoch 秒，
  不含任务 / 尝试 / 工作区编号、事件内容、命令、路径和令牌。

```json
{"schema": 1, "paused_batches": 1, "paused_events": 7, "paused_reason": "http_409", "paused_since": 1790000000,
 "oldest_paused_event_at": 1789990000, "retrying_batches": 0, "retrying_events": 0, "set_aside_events": 0}
```

## 上报给 Valley（`health.outbox`）

协议 2 的库存（`PUT /runner/inventory`）在 `health` 里多带一个字段 `outbox`，内容就是上面这个 schema 1 对象，原样、不加字段。

- 三类分开计数：`paused_*` 是 Runner 因 409 自己停止发送的批次；`retrying_*` 是失败过（含丢回执）但仍在重试的批次；
  `set_aside_events` 是人工丢弃、仍留在本机数据库的事件。只是排队等待发送、没有失败过的结果**不计入**：待处理不等于失败或丢失。
- 没有 `outbox` 字段 = **未上报**（读取失败、对象不合格式，或这个 Runner 不发协议 2）；`outbox` 里的全 0 = 已检查、确实没有。
  读取失败时 Runner 不发送任何猜测的 0，`health` 里的其他字段不变；原因（只记错误类名，不记消息）写进 Agent 日志一次，并记在
  `~/.timetrace/runner_state.json`（`outbox_health` = `ok` / `unavailable`，`outbox_health_error`，`outbox_health_changed_at`；
  `inventory_outbox_reported` 说明最近一次库存是否带了它）。
- 读取不影响领取、上传和审批：它只在库存维护轮里做，失败被吞下并记录。
- 频率有界：最多每 15 秒读一次数据库；只有内容变化或到了原有的 30 秒心跳时才推送。内容里没有随时间自己变化的时间戳
  （`paused_since` / `oldest_paused_event_at` 在批次停止期间固定），所以不会因此每轮写库存。`timetrace agent sync` 会立即重读。
- 同一个 Runner 在批次送达或恢复后，下一次库存带显式的 0（不是字段消失）。
- 协议 1 的 Runner 不读也不发。忽略未知字段的旧 Valley 照常收到库存和心跳；若某个 Valley 用 400 / 422 拒绝带这个字段的库存，
  Runner 立即用同一份、去掉 `outbox` 的库存重发一次，并在 1 小时内不再带它，库存和在线状态不丢。

## 恢复原批次（受控机制）

```
timetrace agent retry-results <job> <attempt> [--yes]
```

- 不加 `--yes` 只显示会恢复多少条。加 `--yes` 后，先把决定写入并强制落盘 `audit.log`（`retry_requested`，写不进去就什么都不改），
  再解除停止；运行中的 Runner 在下一轮把**原始事件原样**再发一次。
- 不重建事件、不续租约、不重新执行任务；Valley 仍然自己决定接受与否。收到 ACK 才标记已送达并清理记录；
  仍被拒收则再连续确认 5 次后再次停止。
- 确认不再需要这些结果：`timetrace agent discard-results <job> <attempt> --yes`（原有的人工丢弃，语义不变：仍保留在本机数据库，不再上传，不算已送达）。

## 降级

新版只新增了表 `remote_outbox_hold`，没有改任何旧表的列（`remote_outbox_retry` 仍是旧版按位置写入的七列）。旧版 Runner 读写同一个数据库不会报错，也不会丢事件；
它不认识“已停止”，会回到每 60 秒重发的旧行为。再次升级后，旧版已确认送达的批次留下的过期记录会在打开数据库时清除。
