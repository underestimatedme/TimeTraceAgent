# TimeTraceAgent 0.6.8

Three things the local queue and the result upload used to get wrong are fixed: a stopped queue no longer leaves a tool running unnoticed, `--after` now waits for its parent, and a result the server keeps refusing stops being re-sent forever.

## What changed

- **Stopping `timetrace run` (SIGINT / SIGTERM).** The scheduler claims no new task, sends SIGTERM to the running tool's process group (SIGKILL after 2 s) and exits only after the kernel confirms the group is gone (ESRCH; EPERM or any other answer is "not confirmed"). The task then ends `failed` with `interrupted (SIGTERM): tool stopped`, its session kept, and the run is marked `interrupted` so the circuit breaker does not count it. It is not re-run on restart: independent tasks continue, tasks that are `--after` it keep waiting, and `timetrace retry <id>` resumes it in the original session. A tool that had already finished stays `done`. If the exit cannot be confirmed, the task says `待核对`, the slot lock stays fenced and `timetrace run` exits 1. After a hard kill (`kill -9`) the next start closes the old record as `待核对`, marks the task `failed` and does not resume it, whether or not a crash fence was left.
- **`--after` waits for the parent.** A child task starts only when its parent is `done`, re-read from the database after the slot is held, again in the claim transaction and again at the spawn gate. A failed parent leaves the child `pending` (`ls` shows `等待前置工作 #N（…）`) instead of marking it `failed`; `timetrace retry <parent>` followed by success lets it start in order. `timetrace retry <child>` can no longer jump ahead of an unfinished parent. A removed parent or a dependency cycle fails the child with a stated reason. Candidates that cannot start are skipped without taking a slot, so independent tasks behind them still run. `timetrace ls --json` gains a `prerequisite` field. Details: [queue-dependencies.md](../queue-dependencies.md).
- **Refused results stop being re-sent.** When Valley answers HTTP 409 five times in a row for the same batch (task / attempt / lease epoch), the Runner stops sending that batch automatically. The events, sequence numbers and times are kept as they were, are not marked delivered and not marked discarded, and the batch does not delay other runs, heartbeats or approvals. `timetrace agent doctor` explains the stop; `timetrace agent retry-results <job> <attempt> [--yes]` sends the original events again (recorded in `audit.log` first); `discard-results` is unchanged. Failures other than 409 (network, timeout, 5xx, 429, 401) are still retried without limit. Upgrading stops nothing by itself: a batch an older Runner kept re-sending is marked for one re-check and stops only if the server refuses it again. Details: [result-upload-refusals.md](../result-upload-refusals.md).
- **Outbox summary in the inventory.** With protocol 2 the inventory carries `health.outbox` (counts of stopped, retrying and set-aside batches/events, one reason code, epoch seconds; no ids, content or paths). A missing field means "not reported", a zero means "checked, none". If a Valley rejects an inventory with the field (HTTP 400 / 422) the Runner re-sends it without the field and leaves it out for an hour.

## Compatibility and rollback

- No server upgrade is required and the execution protocol stays 2. Valley ignores the new inventory field if it does not know it.
- Database changes are additive: a new table `remote_outbox_hold` and a new column `run.interrupted` (default 0). No existing column changed meaning. 0.6.7 and older read and write the same database without error; they do not know about stopped batches (they go back to re-sending every 60 s) or about `interrupted`.
- Do not run an older `timetrace run` after a hard stop without first checking `timetrace ls`: an older queue resets a task left `running` to `runnable` and resumes it, including when its tool may still be writing. See [queue-beside-agent-upgrade.md](../queue-beside-agent-upgrade.md).
- To roll back, reinstall 0.6.7. Tasks left `pending` by `--after` waiting are then marked `failed` (`dependency N failed`) by the older scheduler if their parent has failed, but never started early; the 0.6.8 scheduler puts those never-run tasks back to `pending`.
