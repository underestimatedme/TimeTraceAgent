# TimeTraceAgent 0.6.6

A new approval request now leaves this computer on a path of its own, so a slow upload elsewhere no longer spends its time budget.

## What changed

- Approval requests, their resolution and control acknowledgements are queued the moment the run raises them and uploaded by a small per-job pump: the attempt's whole unacknowledged tail, without the global flush lock, with a 2.5 s per-request timeout and one immediate retry, at most 3 uploads of an attempt in flight. What it cannot send is retried on the existing backoff. A conflict (HTTP 409: the attempt ended, was cancelled, fenced or lost its lease) is kept and retried rarely, exactly as before; a 401 is left to the normal flush.
- The pump wakes only for approval and control events and sends only events before a run's first result event (`completed`, `failed`, `cancelled`, `waiting_*`). Runs without approvals or control events, and every result event, take exactly the path they took in 0.6.5. The normal flush lets an approval-path upload of the same attempt finish first (bounded) instead of sending the same events beside it.
- Valley already applies an attempt's events strictly in sequence, skips every event at or below the sequence it holds before validating, and acknowledges only after the commit, so overlapping, replayed or late-arriving uploads change nothing. A slow upload that fails after a newer one had the same events acknowledged no longer sets a backoff.
- The Agent log says where delivery time goes (timings and job ids only, never event content): `slow upload: lock_wait=…s post=…s batches=…` for a flush of 2 s or more, `approval request waited …s before it was queued` and `approval upload n/2 for job … failed after …s` when the fast path struggles.

## What it does not promise

The budget it is built for: the Runner asks, Valley holds the request within 5 s (a healthy upload took 1-2 s in production; one lost request adds 2.5 s), which leaves a web page its 4 s poll and one read inside 10 s. If Valley itself is slow or down for the new request too, nothing on this computer can deliver sooner: the events wait for the backoff and go out when Valley answers, in order, once.

## Compatibility and rollback

No event content, sequence number, wire format or database schema change; execution protocol stays 2 and neither Valley nor the web page needs to change or be released first. A 0.6.5 or older Agent keeps the previous (slower) delivery. To roll back, reinstall 0.6.5; the outbox is readable by both.

## Validation before release

Python 3.12 full test suite on the exact release commit through the pinned `agent-candidate` job in the TimeTrace web CI, plus `pip wheel . --no-deps`. `tests/test_approval_delivery.py` replays the 2026-11-12 proportions at x0.25 in real time. Installed test machine before this release: 0.6.4.
